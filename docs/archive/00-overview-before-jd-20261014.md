## 1. 文档分工

本仓库维护本总计划与项目二实施计划；项目一计划由 RK 侧独立维护。本项目的详细架构、记忆系统和验收标准统一放在项目二计划中。

项目二首版采用 **Pipecat1.12.0 主控、Mem02.2.1 长期记忆、APScheduler3.11.3 持久提醒**，主要业务编排使用 Python；现成模型后端采用 llama.cpp、OpenVoiceStream、yolo_ros/TensorRT 和 ROS2 Jazzy。记忆使用 Qdrant local、SQLite history和CPU BGE；必要薄适配/操作journal补足主体、更正、遗忘和跨存储恢复。模型及边界以[实施计划第 3 节](../../02-jetson-multimodel-inference.md#3-开源组件选择与固定版本)为准，不另造主控/向量引擎。Qwen2.5-VL-3B为首轮模型基线；Letta/Triton只作参考，Edge-LLM对话后端放在J5.7后续性能对比，J0功能闭环仅采用llama.cpp。

## 2. 求职目标与现有基础

### 2.1 目标定位

目标是在机器人行业内，从已有底层与中间件经验延伸到端侧 AI 部署、机器人软件系统集成与推理性能优化，而不是转向纯语音算法研究。

目标能力表述：

> 能在真实机器人上完成端侧模型与外设的工程集成，打通业务闭环；能定位多模型运行中的系统瓶颈，并用可复现数据证明优化；能在 Rockchip 与 NVIDIA 平台分别完成适配和验证。

本计划面向机器人端侧 AI 部署、嵌入式 AI、机器人软件系统及边缘推理优化等岗位方向。岗位名称以实际 JD 为准，这里定义能力目标，不承诺特定公司招聘要求或录用结果。

### 2.2 已有经验如何衔接

当前工作涉及电机驱动库、Linux 外设驱动、中间件、USB-CAN 中间件及底层嵌入式代码。两项目利用这些经验，向上覆盖模型、推理服务、业务状态与性能分析，不需要舍弃已有积累后重新做纯算法项目。

| 能力方向 | 已有经验的连接点 | 需要补充的项目证据 |
|---|---|---|
| 设备与系统集成 | 外设接入、驱动、总线、中间件 | 真实数据流、资源所有权、设备恢复、时间与坐标标定 |
| 完整机器人软件 | 电机接口、控制反馈、嵌入式状态 | 语义任务到动作闭环、取消/去重/有效期、结果判定与有限恢复 |
| 端侧模型部署 | Linux、板卡与运行环境 | 模型转换、后端兼容、精度回归、资源预算与部署复现 |
| 推理性能优化 | 多线程与系统调试基础 | CPU/GPU 时间线、排队/传输/计算拆分、并发干扰、单因素实验 |
| 跨平台工程 | 多类硬件与接口适配 | 公共契约与平台专有实现分离，两端都有实际部署和验收 |

ASR、TTS、LLM/VLM 和视觉模型是机器人业务组件与优化负载，不把项目写成语音模型研发。应用部署和性能优化也不自动等同于自研推理引擎、编译器或 CUDA 算子能力；未实际完成的技术深度不写入成果。

## 3. 两个项目的定位与差异

| 维度 | 项目一：Edge Voice Manipulator | 项目二：Local Multimodal Assistant |
|---|---|---|
| 平台 | RK3588 16GB/128GB + PCIe RK1828 | 本机已读取为 Orin NX，约16GB内存、L4T 39.2.1；JetPack 套件与完整兼容性继续核验 |
| 核心问题 | 如何把语音输入到真实执行与反馈做完整、做可靠 | 真实机器人多模型共同运行时，如何解释并改善性能 |
| 真实场景 | 中文指定桌面物体与目标区，机械臂抓放、验证、恢复 | 持续感知、对话、看图、打断、长期记忆、有限工具与主动提醒 |
| 工程主线 | 外设、异构部署、通信、任务状态机、动作及恢复 | 成熟框架集成、部署、profiling、多模型准入/资源与数据路径、质量/性能权衡 |
| 独立成果 | 一套可独立运行的语音到执行机器人应用 | 具有长期记忆的本地多模态助手，以及有真实业务基线和对照证据的推理优化实现 |
| 首要指标 | 任务正确率、抓放成功率、失败识别/恢复、稳定性 | 尾延迟、结果时效、违约/丢弃率、有效吞吐量、内存与功耗 |
| 能力证明 | 能把系统做完整 | 能找出瓶颈并把系统优化好 |

两者允许采用相似模型、外设或语音基础。区别在核心问题、独立修改和验收证据，而不是为了表面差异强行选择完全不同的功能。RK 的性能测量用于保证应用可用，Jetson 的业务闭环用于保证优化具有真实意义。

两个项目在线运行相互独立。RK 不依赖 Jetson 计算，Jetson 不依赖 RK 补算；离线训练、标注、转换可以使用另行确认的开发设备，不混为端侧在线能力。不能只把 RK 项目换成 TensorRT 再记作第二项完整成果。

## 4. 跨平台能力如何验证

跨平台不只意味着用过两块板，而是能解释可复用部分、平台差异和验证方法。

| 层次 | 可以复用 | 必须分别验证 |
|---|---|---|
| 行为契约 | 请求/任务 ID、时间戳、取消、有效期、结果与错误语义 | 各后端停止提交、清理队列和实际设备反馈的行为 |
| 数据与评测 | 授权语料、输入格式、精度集、阶段命名和统计方法 | 输入预处理、数值误差、时钟映射与采样链路 |
| 推理部署 | 支持条件相同的 checkpoint、模型清单与版本方法 | RKNN2/RKNN3、TensorRT 或其他后端的模型产物、算子与精度支持 |
| 运行时 | 有界缓冲、状态管理、健康检查的设计经验 | CPU/NPU/GPU 执行、PCIe、内存分配/拷贝与并发策略 |
| 外设 | 相机、声卡和执行器的职责与接口 | BSP/驱动、USB 拓扑、供电、设备枚举和故障恢复 |

跨平台交付延续两份项目计划已有要求：

1. 选一个两端都实际支持的视觉 checkpoint，固定输入与后处理，记录精度、执行时间、数据路径和资源占用。模型/精度不同只能比较产品方案，不能声称同模型加速比。
2. 选择同一个取消/过期请求用例，分别证明两平台能够阻止旧结果污染新任务；RK 侧另验证旧结果不能重新触发动作，Jetson 侧验证旧播报/工具回调隔离；解释平台后端不同但行为契约一致。
3. 列出公共接口、平台适配和业务专属代码的边界；只抽取已出现的重复，不预先搭建跨平台万能 SDK。
4. 保留两端独立的软件/模型/驱动清单、部署过程和验收记录；同一项复用工作只认领一次。

## 5. 硬件与资源安排

| 资源 | 使用安排 | 已知边界 |
|---|---|---|
| RK3588 + RK1828 | 项目一在线计算 | 16GB/128GB、内核 6.1.118、PCIe 已由用户确认；具体板型、RK1828 内存、BSP/SDK/模型兼容仍需核验 |
| Jetson Orin NX 16GB | 项目二在线计算 | 已读取设备树与软件包信息；模块 SKU、JetPack 套件、功耗与散热继续实机核验 |
| D435i | 两项目分时使用 | 当前Jetson已枚举D435i，USB速度480Mbit/s；USB3链路、RGB-D帧率/同步仍需验收；不默认第二台相机 |
| SO-101 主从臂 | 仅用于 RK 完整抓放；项目二不使用实体执行器 | follower 执行，leader 用于标定/示教；RK 侧保留夹爪，不做台灯构型 |
| 接触/压力传感器 | RK 多传感器闭环 | 安装、接口与采样待验证，不假设已具备力控能力 |
| 麦克风与扬声器 | 两项目按需分时使用 | 型号/AEC 能力尚未确定，不因有 VAD 就宣称全双工 |
| 公司产品与接口 | 获得授权后可用于真实业务接入 | 未接入不得宣称公司产品验证；不使用未授权源码、数据或权重 |

优先利用现有设备完成两个独立项目，不以购置新底盘、第二套机械臂或额外服务器为前置条件。物理保护、限位、停止和重新使能保持独立于模型；长时稳定性测试不等于无人值守或工业安全认证。

## 6. 整体推进方式

| 顺序 | RK 侧里程碑 | Jetson 侧里程碑 | 共同产出 |
|---|---|---|---|
| 平台核验 | OVS/RKNN/RK1828 最小验证、外设与运动安全门槛 | 模块/JetPack、模型后端与设备最小验证 | 明确兼容性、可用资源与风险，不提前承诺加速能力 |
| 建立基线 | 先受限动作、固定抓放，再接入多传感器与语音 | 先真实交互，再建立完整时间线和串行/直接并发基线 | 可重复输入、请求/时钟规范与初始问题记录 |
| 深化各自重点 | 抓放验证、失败恢复、双加速路径与整机可靠性 | 并发调度、数据/执行路径、质量约束与单因素优化 | 各自独立的工程贡献和原始测量 |
| 最终验收 | 按 RK-01 至 RK-09 完成 | 按 JT-01 至 JT-13 完成 | 两平台复现、跨平台说明、公开作品集 |

两项目可交错推进，不要求先完成全部 RK 才能开始 Jetson；共享实体设备时分时使用，其他阶段可用授权回放。具体任务顺序以各计划书为准，不把两份计划中的复用工作重复计入工时。

完成平台核验与第一轮基线后再估算剩余工时和日期；不沿用已废弃的旧 Jetson 抓取工时。本次文档整理不调整课程或 learning log 排期，也不新增固定截止日期。
