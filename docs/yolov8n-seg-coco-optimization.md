2026-10-21。按用户“假设选择 COCO”的方案组织。**同一个 YOLOv8n-seg，分别走完模型本体优化和部署运行优化，再组合有效改动。** 用户亲自操作、修改、训练和测量，助手负责分步指导、源码解释与结果分析。

本轮只研究这个模型及其图像输入→预处理→TensorRT→后处理→结果路径。十模型系统集成不作为本轮前置任务。COCO 结果用于本案例的可比效果和性能评估，不能直接宣称家庭场景已经验收通过；家庭数据与真实相机验收在此案例之后补充。

## 2 准备 COCO 及用途划分

选择 **COCO 2017 instances**，同时保留检测框和实例分割标注。[COCO 分割数据说明](https://docs.ultralytics.com/datasets/segment/coco/)

| 数据 | 用途 |
|---|---|
| `train2017`：118,287 张 | 后续 QAT、剪枝后微调；从中固定抽取 PTQ 校准子集 |
| `val2017`：5,000 张 | 本轮开发评测与最终留出评测的来源 |
| `instances_train2017.json` / `instances_val2017.json` | 原生 COCO 真值；用于框和 mask 的正式评测 |

为了练习完整实验管理，建议在开始前固定随机种子和图像 ID，把 val2017 分为 1,000 张开发集与 4,000 张最终留出集。开发集用于调试、比较、选方案；最终留出集在方案冻结后比较原版与最终候选，不参与训练、校准或调参。这里的“留出”是本次优化实验的使用约束，不宣称公开预训练模型从未利用过 COCO 验证数据做历史选型。

最终可以额外报告整个 val2017 的官方口径结果，但要注明它包含开发集；1,000/4,000 子集结果不能冒充官方完整 5,000 张成绩。如果选择反复使用整个 val2017 选方案，就明确称其为验证集对照，不把它宣称为独立最终测试。

PTQ 校准可先固定 500～1,000 张训练图片作规模起点，覆盖目标大小、目标数量、背景和场景变化；数量是否足够由开发集效果验证。校准通常不要求人工标签，QAT/剪枝微调和效果评测需要对应标注。

保留无人和其他类别图片，不能只测检测成功的人体图片。先保留 80 类完整标注，只单列 person 指标；不要把其他类标签删除后仍声称原 80 类任务不变。COCO 的 person category_id=1，而模型 person class_id=0；完整类别映射不能简单地把所有类别索引加 1。

最先只准备 val2017 图像和 instances 标注，用少量固定图检查评测链路，再扩展到开发集。训练图像等进入校准/训练阶段再准备；全量训练数据优先放在独显设备上。

## 3 先建立效果与部署双基线

### 效果基线

先评测已有 PyTorch 权重，再评测已有 FP32 TensorRT 引擎。如果同输入下导出前后的结果存在明显差异，先检查颜色、归一化、补边、坐标还原、类别映射、NMS 和 mask 解码，不能把导出错误归入量化损失。

同时记录：person box AP50、AP50–95、person mask AP、业务阈值下 Precision/Recall，以及 80 类 box/mask mAP。保留典型漏检、误检、遮挡和小目标案例。

需要分别保留两个口径：

1. **标准效果对照**：固定验证预处理、候选保留阈值、NMS 和评测器，使用低置信度截断保留 PR 曲线所需候选；记录 COCOeval 的 `maxDets` 等设置。所有候选使用相同口径。标准推理阈值、尺寸与参数以固定版本的验证程序为准。
2. **项目实际部署效果**：使用本项目真实预后处理和阈值。当前置信度为 0.25、NMS IoU 为 0.45、最多保留 10 个总目标；这会改变结果集合，因此与标准 AP 分开命名，不能直接与官方模型表横比。

Ultralytics 验证可用来建立 PyTorch 参考，但需要固定 batch、640 方形输入、补边等参数；不要拿矩形验证路径与固定 640×640 引擎当成完全相同的输入。当前引擎由项目构建，不预设它可直接交给其他框架的 `.val()`；最终部署效果应由项目适配器输出框/原图 mask，再送入统一 COCO 评测器。使用 [Ultralytics 验证工具](https://docs.ultralytics.com/modes/val/) 和 [官方 COCOeval](https://github.com/cocodataset/cocoapi/blob/master/PythonAPI/pycocotools/cocoeval.py)，避免自己重新实现 AP 和 crowd/ignore 规则。

若标准口径需要与项目部署不同的后处理容量/阈值，只在独立的评测配置中声明，分别评测原版和候选；不改生产阈值让成绩看起来更好。

### 部署基线

只在同一 Jetson、相同输入顺序、功耗/时钟策略、预热和后台负载下比较运行性能。PyTorch 在训练服务器上的速度不与 Jetson TensorRT 速度直接算加速比。

| 层次 | 指标和工具 |
|---|---|
| 引擎 | trtexec；GPU 执行、传输、提交与工具吞吐 |
| 单模型完整调用 | 项目适配器的 P50/P95，包括预处理、原生执行和后处理 |
| 文件/流输入路径 | 图像解码、输入等待、调用和结果发布分别记录；不把磁盘 I/O 混称为引擎耗时 |
| 资源与持续状态 | 进程内存、板载可用内存、整板功耗、温度和实际时钟；明确采样周期及统计窗口 |

从开发集固定选一组有代表性的性能输入，所有候选使用同一份图像 ID 与顺序。记录逐次数据、失败和样本数，分开统计冷启动、预热、稳态。

COCO 静态图片没有天然的视频到达时间；连续回放时必须声明输入速率和观察位置。离线吞吐不是家庭相机处理 FPS，也不能靠 `1000/单帧时延` 推导完整应用帧率。模型引擎的同输入短 trace 用于归因，不作为无 profiler 的正式耗时成绩。

**阶段产物：** 原始 PyTorch 质量报告、FP32 引擎质量报告、Jetson FP32 性能/资源报告、固定输入及评测配置。这一步不需要训练。

## 4 路线 A：保持权重与精度的部署优化

从原始 FP32 工件开始，只改变执行实现。先用阶段计时和 nsys 判断时间分布；CPU Python 热点用 cProfile/pstats，原生 CPU 热点与调度按需要用 perf；只有确认 GPU kernel 值得深挖时才用 ncu。

| 证据 | 可尝试的单项改变 | 验证重点 |
|---|---|---|
| 预处理反复分配/转换 | 缓冲复用、减少中间张量或重复转换 | 输入张量、输出语义和端到端耗时 |
| 后处理 CPU 成本大 | 向量化、减少 Python 对象转换、优化 mask/NMS 实现 | 框、类别、分数、mask 一致性或任务质量 |
| 主机复制或同步成本高 | 明确缓冲所有权，减少确认多余的复制/等待 | 无错帧、无覆盖输出、无竞态与异常泄漏 |
| 提交开销或流水空隙明显 | 按需评估 CUDA Graph、CPU/GPU 重叠、同模型多缓冲流水线 | 真实重叠、完整 P95、内存与结果新鲜度 |
| Python 自身成为瓶颈 | 对具体热点做 C++/CUDA 实现或调用优化库 | 同算法/同工件下的收益；不预设全面重写更快 |

这是单模型案例；“并行”在这里可以指该模型不同阶段/输入之间的流水线，不增加 YuNet、RTMW 等其他模型来改变研究对象。是否值得并行由关键路径决定。每项改动后重测效果与性能，保留一个有明确证据的部署候选 R1。

## 5 路线 B：模型本体优化

以下候选先使用原始部署实现 R0，便于区分模型变化与路线 A 的收益。所有候选都重新做最终引擎的质量、耗时和资源评测。

| 候选 | 具体工作 | 训练要求 | 核心对照 |
|---|---|---|---|
| M1：FP16 | 从原始浮点模型构建低精度 TensorRT 候选，检查实际层精度、转换和回退 | 通常无需训练 | 原 FP32 对比 FP16 的效果、完整调用和资源 |
| M2：INT8 PTQ | 固定校准集，使用真实预处理收集校准信息，导出受支持的量化图/工件，再在 Jetson 构建 | 不更新训练权重 | 与原版/FP16 比较；检查性能是否被非量化层和转换开销限制 |
| M3：INT8 QAT | 从浮点权重或受支持的 PTQ 初始化开始，在 PyTorch 中加入量化模拟并微调；导出并验证 | 需要训练/微调 | 相同评测下是否改善 PTQ 的质量；学习对照可做，生产采用按收益决定 |
| M4：结构化剪枝 | 建立依赖图，分档剪通道/模块，保护检测与分割输出契约，再微调恢复效果 | 通常需要微调 | 剪枝前、剪枝后未恢复、微调后都记录；先与相同精度原模型比较 |

量化工具可从 [NVIDIA Model Optimizer](https://nvidia.github.io/Model-Optimizer/guides/_basic_quantization.html) 评估。具体 YOLOv8n-seg 自定义模块、fake-quant/QDQ、ONNX 算子及 TensorRT 10.16 兼容性，先用少量输入跑通；不承诺一个通用开关即可完成。不能把使用随机量化范围的 INT8 测速引擎当作完成真实 PTQ 校准的成果。

结构化剪枝可参考 [Torch-Pruning](https://github.com/VainF/Torch-Pruning)。需要处理 C2f、拼接/残差等结构依赖，保持类别数、框与 mask 系数/原型的外部契约。只把权重置零不等于结构变小，也不自动带来 TensorRT 加速。所有剪枝候选都需重新导出和构建引擎。

如果原模型已满足 COCO 质量要求，无需在起点额外进行一次普通训练。训练主要出现在 QAT 和剪枝后的恢复阶段。固定训练数据、训练预算、seed、学习率计划和选模规则；损失下降仍需落实到独立评测指标。

| R0 | 原始 | 原始 FP32 | 待测 | 待测 | 待测 | 待测 | 基线 |

| M1 | 原始 | FP16 | 待测 | 待测 | 待测 | 待测 | 低精度取舍 |

| C | 部署优化 | 最佳模型方案/有效组合 | 待测 | 待测 | 待测 | 待测 | 最终方案 |

质量门槛、允许下降幅度与主要性能目标先登记。以“效果满足要求且有可重复的部署收益”为保留依据，不只看参数量、FLOPs、engine 文件名或某一次最快值。未改善、退化、无法导出的尝试同样保留原因。

如果需要给出整板能耗，说明是否按固定输入窗口的板端能量除以完成数计算；不能把 GPU 利用率当成耗电，也不能把整板功耗称为单模型独占功耗。

## 7 当前先做什么

当前只进入数据与原始效果基线阶段：

1. 准备 COCO val2017 图像及 instances 标注，检查图像、框、mask 和类别对应关系。
2. 固定开发/最终留出 ID，记录评测配置；先少量图片验证输出与标注对齐。
3. 使用现有 `.pt` 和 FP32 `.engine` 建立开发集效果基线，再补同条件部署性能基线。

现有 `vision_b1_modules.py` 只覆盖冻结的少量图片，并不是 COCO AP 评测器。COCO 全数据评测和项目部署输出转换入口仍需逐步接通；不能把已有的三图一致性报告当作完成了 COCO 评测。本轮仅整理路线，未下载数据、训练、生成引擎或代做优化。
